# Feishu Base through Lark CLI

Briefwright uses `lark-cli` as its only Feishu transport. Install and authenticate it first, then verify `lark-cli whoami`. Conversational setup accepts either the Base app token or a direct official `feishu.cn`/`larksuite.com` `/base/...` link. Wiki links are rejected because a Wiki node ID is not a Base app token; open the underlying Base and copy its direct link.

```yaml
processStore:
  driver: lark
  baseToken: YOUR_BASE_APP_TOKEN
  identity: user
```

By default Briefwright resolves the portable standard table names `数据源`, `运行批次`, `情报条目`, `状态事件`, `人工反馈`, `优化实验`, `原始采集`, `规则版本`, and `扫描回执`. It never falls back to table IDs from another user's Base. Existing deployments may override any mapping with their own table name or ID.

For a new or partially prepared Base, run `briefwright lark provision --yes`. Provisioning is idempotent: it creates only missing standard tables, scalar fields, and relationship fields. It never deletes or renames a table or field and never overwrites a record. Duplicate standard table names or a configured missing `tbl...` ID fail closed.

Capacity rollover uses a parallel generation of all nine tables, not deletion or in-place relation retargeting. Configure a new, consistently suffixed set of table names, preview the effective configuration, then explicitly approve provisioning. Run online doctor and a read-only sync plan before any apply. The old generation remains a read-only archive. Briefwright keeps detailed internal item-transition telemetry in SQLite and projects only run/failure events plus final Daily/Review transitions into Base, but captures, receipts, and items still require a planned generation boundary before their real table limit is reached.

`briefwright doctor --online` checks the CLI version, identity, access to all nine tables, required fields, and a record-upsert dry-run. `briefwright import lark` paginates all nine tables, resolves links to stable business IDs, validates every canonical record, creates a content-addressed local snapshot, and imports the history into the local evaluator; it makes no Base changes. `sync plan` lists creates, updates, unchanged records, conflicts, and a digest. Only `sync apply --yes` writes.

`briefwright lark audit` is the stricter read-only data gate. It paginates every field and record in all nine tables, rejects fields that are absent from the versioned production inventory, checks observed field types, and reports full-table, partial, and core-row blank counts. A provisioned schema can therefore pass while historical rows still fail the audit; provisioning columns is not treated as a data backfill. System-generated fields, historical compatibility fields, and managed writable fields are inventoried separately. Historical values that cannot be derived from durable evidence must remain an explicit migration gap rather than being fabricated.

JSON values larger than the process-store safety budget are represented in Base by an explicit envelope containing the original byte count, SHA-256 digest, a short preview, and `storage: local-runtime-journal`. The complete durable payload remains in SQLite. This is an intentional auditable reference, not a silent truncation or an invented replacement value.

`briefwright lark backfill` is a dry-run by default. It joins the local SQLite journal to existing Base business IDs, includes the production compatibility columns in comparison, and plans updates only for rows present on both sides. Local-only rows are reported and skipped, so a backfill cannot reverse an intentional Base data-retention or slimming operation. The write form requires `lark backfill --apply --yes --expect-digest <reviewed-sha256> --expect-updates <reviewed-count>`; the command recomputes the plan and refuses all writes if either bound value changed. It performs no creates or deletes and requires the normal per-record relationship resolution and readback acknowledgement. Rows without durable local evidence remain visible in the next audit instead of receiving invented defaults.

Reads are projected and paginated. Writes use stable business IDs to find record IDs, upsert scalar fields, then resolve relationship fields in a second pass. Existing source and rule records are treated as control-plane owned and are not overwritten by normal run synchronization. No normal command deletes a record or changes table structure.

The current source importer maps GitHub release pages to the GitHub API, arXiv list pages to RSS, and remaining public URLs to the bounded webpage connector. X profiles map either to the official X API or to the `codex-browser` bridge selected by `processStore.xCapture`. A non-X source whose `采集方式` is `Codex Browser` uses the isolated in-app Browser bridge; it never takes over Chrome or the desktop foreground. A source explicitly set to `Computer Use` uses the local App/UI bridge instead. `capture manifest` freezes only currently due sources, entry URLs, exact allowed hosts, interaction policy, and the expected bundle path. `capture validate` enforces freshness, size, capture mode, source binding, clean HTTPS URLs, exact host membership, and one explicit captured/unchanged/failed outcome per source. Browser and Computer Use timestamps must declare whether they are event dates or page-update metadata; page-update metadata never satisfies event freshness. Unsupported, unavailable, missing, or out-of-bound sources fail visibly in their receipts.

Every explicit URL produces a capture record. Successful records include the available HTTP status, content type, language, author or organization, original publication value, ETag, Last-Modified, content hash, and parser version. Failed fetches also create a capture record with attempt count and failure reason, in addition to the source receipt. Protected source text is limited to a 25-word persisted excerpt; a bounded full body can be used transiently by the current model call but is stripped before the capture enters SQLite, Base, snapshots, or logs.
